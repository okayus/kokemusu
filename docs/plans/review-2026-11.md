## ① 依存の更新とセキュリティヘッダの固定

- 実測: lockfile は 2026-09-04 から変わっていない。`pnpm audit --prod` は 11 件を報告する（zod high 1、hono moderate 9・low 1）。
- 実測: hono 4.13.3 は、改行（`%0A` / `%0D` / U+2028）を含むパスに wildcard middleware を掛けない（GHSA-h7mg-cq63-vhpq、4.13.16 で修正）。本番でも `securityHeaders` が外れ、`/x%0A` は SPA の HTML を CSP・X-Frame-Options・HSTS・nosniff なしで返す。
- 実測: 認証は素通りしない。単体ハーネスで 24 route に改行入りの変種を 1,812 通り送り、保護 route はすべて 401 / 403 か SPA fallback だった。

## ② 空の石を補完から外す

- コードから: `GET /api/tags`（`worker/routes/tags.ts`）は苔片が 0 の石も返す。石を消す経路は無い。
- 付け替えで `TS` を `typescript` に寄せても、タグ欄で「t」と打つと `TS` が `typescript` より先に候補に出る（候補は norm 順で、Enter は先頭を取る）。打ち間違えた石も残り続ける。
- 直し方: `/api/tags` の WHERE に `EXISTS (SELECT 1 FROM post_tags WHERE tag_id = tag.id)` を足す。石は苔片に付ける操作でしか生まれないので、空の石は残骸である。
- 行は消さない。同じ綴りでまた積めば、同じ石（id・色）に戻る。
- 2026-11-14 まで status にあった問い「統合に使うと空の石が残る → タグ運用の統合 / 削除が要るか」への最小の答えである。石の統合・削除の機能が要るかは、実データ目視で決める。
- 確かめ方: e2e のゴールデンパスで、付け替えで空になった石が候補に出ないこと。

## ③ 付け替えの `add` に上限

- 実測（`toSQL().params.length`）: 付け替えの `UPDATE` は、足す石がすべて既存のとき `1 + 絞り込み + 足す + 外す` 個を bind する。最悪は 144（20 石 ＋ 期間両端、足す 99、外す 20）で、1 石・期間なしでも足す 99 で 102 〜 103 になる。D1 の上限は 1 文 100。
- 100 を超えるのは、足す ＋ 外す が 76 以上（1 石・期間なしなら 98 以上）のときである。UI からは現実的に踏まない。
- 直し方: `retagSchema.add` の上限を `MAX_TAGS_PER_SET`（20）にする。最悪は 65 になる。`posts.test.ts` の「binds the filter and the stone」を最悪値（20 石 ＋ 期間両端、足す 20、外す 20）で測り直す。`features.md` §2 に上限を 1 行足す。
- 送り側の契約（`createPostSchema`）は変わらない。タグ欄（`MAX_TAGS` 99）を付け替えの「足す石」だけ 20 にするかは、実装時に決める。

## ④ Cron で期限切れ session を掃除

- コードから: `worker/cron.ts` はログを出すだけで、毎時 1 回なにもしない。`data-model.md` は「期限切れは提示時に lazy 削除 ＋ Cron で掃除」と書いていて、`session_expires_at_idx` もそのためにある。
- 提示されなくなった session（cookie を消した・別の端末）の行は残り続ける。
- 直し方: `runScheduled` で `DELETE FROM session WHERE expires_at < now` を 1 文走らせ、消した件数をログに出す。
- 確かめ方は、実装時に Cloudflare の docs（scheduled handler のローカル実行）で確認する。

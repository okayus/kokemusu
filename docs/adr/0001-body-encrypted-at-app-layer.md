# 本文はアプリ層で暗号化する（鍵は Worker Secret）。メタデータは平文

苔むすはプライベートな本文（思考・学習・お金の話）を Cloudflare D1 に置く。D1 ダンプ・バックアップ・
D1 権限付き API トークン（Workers Builds のビルドトークン等）の漏洩で本文が読めてしまうのを防ぐため、
**Worker が保存時に本文（と見出し）を AES-GCM で暗号化し、読み出し時に復号する。鍵 `BODY_KEY` は
Worker Secret（同じ値を 1Password にも控える）。日時・タグ・件数などのメタデータは平文のまま**にして、
可視化と集計をサーバ側で成立させる。最初の実データより前（Phase 1）に入れ、平文の本文が
D1・Time Travel・バックアップに残る期間を作らない。

## Considered options

- **(A) インフラ暗号化のみ**: 最も単純で FTS5 がそのまま使える。ファイル / トークン漏洩 = 本文流出。
- **(B) を Phase 3 で**: MVP は平文。縦切りは最短だが、それまでの平文がバックアップに残る。
- **(C) 端末側 E2E（パスフレーズ由来の鍵）**: Cloudflare にも平文を渡さない最強案。しかし
  mazuoboeru からの PAT 自動投稿（サーバ間 HTTPS）は鍵を持てず平文で届く、サーバ検索が不可能、
  端末ごとにパスフレーズ入力、紛失で全損 —— 「摩擦ゼロ」と API 自動投稿に直接ぶつかる。

## Consequences

- Cloudflare 自身（インサイダー・法的要請）と Worker コードの侵害は守備範囲外。VPS のホスティング
  業者と同程度に信頼する、という線引き。
- 全文検索は FTS5 ではなく、期間で絞って復号して走査する（個人規模では十分。重くなったら端末内索引）。
- `BODY_KEY` を失うと本文は永久に復号不能。`wrangler secret put` と同時に 1Password へ。
  ローテーションは暗号文の鍵 ID（`k1.`）で世代管理し、順次再暗号化する。
- API 自動投稿は Worker 到着時に暗号化されるので手動投稿と同じ扱い。送り側は鍵を持たない。
